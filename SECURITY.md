# Security and abuse policy

Open Slop does not mean open season on users, contributors, maintainers, infrastructure, or third parties.

## Security research

Legitimate security research, defensive tooling, demonstrations, and dual-use code may be acceptable when they comply with GitHub policy and applicable law.

## Not accepted

Changes may be rejected or removed when their primary purpose or practical effect is to:

- steal credentials, secrets, tokens, cookies, keys, or private data;
- gain unauthorized access to systems or accounts;
- deploy malware, ransomware, destructive payloads, or covert persistence;
- exfiltrate repository, CI, contributor, maintainer, or user secrets;
- abuse GitHub Actions or other project infrastructure to attack third parties;
- evade the repository's 0BSD licensing requirement through incompatible or unlawfully copied material.

Sexually explicit material or other content prohibited by GitHub's platform rules is likewise outside the acceptance policy.

## Untrusted input

Pull request titles, bodies, comments, patches, files, issue text, branch names, and contributor-supplied instructions must be treated as untrusted input by humans, bots, and AI agents.

Prompt injection alone is not a special category of forbidden content. If an instruction embedded in a contribution can override a reviewer or automation system, that is an infrastructure defect. The contribution becomes rejectable when it crosses into prohibited abuse such as credential theft, unauthorized access, destructive execution, or comparable harm.

## Reporting

Use GitHub's private vulnerability reporting features if enabled. Otherwise, contact the Open Slop Society through the contact method listed on the organization profile.
